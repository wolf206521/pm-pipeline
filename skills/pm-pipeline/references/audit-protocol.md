# AUDIT-PROTOCOL · 需求完整性审计协议 v1(通用模板)

> 用途:对权威需求基线(全模块说明书 + 设计大纲)做独立审计,检查需求/状态/功能的关联、孤岛与逻辑遗漏。
> 本文件是方法论,可复用;审计报告是项目产物,放 `02-需求输入/`。

## 审计对象与锚点

- 主对象:`02-需求输入/提取缓存/` 下按模块拆分的权威说明书
- 全局约定:拆分产物中的全局约定篇
- 作者自查结论:基线文档附录(如有)
- 大纲:提取缓存中的设计大纲

## 独立性原则(重要)

若需求文档作者已做过自查并声称问题全部闭环,**审计不是复述作者结论**:

- 作者声称已闭环的条目要**抽查验证**,找到正文证据才算数
- 与作者结论矛盾的发现优先级最高,必须给原文引用
- 没有发现就说没有发现,不硬凑

## 检查维度

### 1. 状态孤岛

- 每个对象状态集合:每个状态是否有进入路径(谁写入/什么事件触发)、退出路径、可到达的终态
- 只出现一次、没有任何流转说明的「僵尸状态」
- 被其他模块/矩阵引用但本模块未定义的状态 → 悬空状态
- 状态回退是否只指向可修正节点,是否有补偿规则

### 2. 功能孤岛

- 每个子模块/功能点:上游输入(谁触发、数据从哪来)、下游消费(产出给谁)、操作角色、关联状态
- 无下游消费者的功能 = 疑似孤岛(报表/看板等终产物除外,但需说明)
- 别的模块引用本模块的功能/接口/事件,本模块没定义 → 断链

### 3. 事件与接口配对

- 本模块发布的事件:有无消费者?payload 是否满足消费者需求?
- 本模块消费的事件:生产者是否定义?契约是否一致(版本、幂等键)?
- 「由 <模块> 回传/同步/提供」类表述:对端模块是否真有对应功能

### 4. 需求→功能覆盖

- 该模块在大纲中的子模块清单与说明书是否一致(大纲只作边界基线,字段级以说明书为准)
- 大纲主流程在该模块的落点是否都有功能承载

### 5. 逻辑遗漏

- 异常分支(失败/超时/重复/越权)是否都有出口
- 金额/数量字段有无单位与口径;前置条件有无强制点(门禁)
- 角色名是否能在角色体系中找到对应
- 「待补」「待定」「另议」类悬空表述

## 输出格式(严格遵守)

```
### 模块:<编号> <名称>
结论:通过 / 有发现(N 项:P0×a, P1×b, P2×c)

| # | 严重度 | 类型 | 位置(章节号) | 问题描述 | 证据(原文引用) | 建议处置 |
```

- 严重度:**P0**=业务错误或阻断开发(矛盾、断链、状态不可达);**P1**=必须修正的逻辑缺口;**P2**=建议改进
- 类型:状态孤岛 / 功能孤岛 / 事件断链 / 覆盖缺失 / 逻辑遗漏 / 与作者结论矛盾
- 每条必须有原文证据引用;没有证据的怀疑写进「待核实」清单,不算发现

## 附:PRD ↔ 原型覆盖核对(S4 阶段使用)

原型页面产出后,反向核对需求覆盖,防止「页面是页面、需求是需求」两张皮:

1. **提取 PRD 清单**:功能需求条目 / 用户故事(正常+异常流程)/ 状态机状态与流转 / 异常矩阵 / 字段字典 / 埋点
2. **对照页面 manifest**:每条需求找页面落点(区块/字段/操作);找不到 = 遗漏
3. **输出四类结论**:完全遗漏(零落点)/ 覆盖不足(缺关键要素)/ 覆盖率统计(功能点 x/y、状态 x/y、字段 x/y、异常 x/y)/ 页面超出 PRD(疑似发明或 PRD 缺口,须裁决)
4. **机检辅助**:`--prd` 交叉核对(manifest 字段名/必填/类型 vs PRD 字典、状态枚举 ∈ PRD、操作有 PRD 出处)
5. 缺口修复后回归;「页面超出 PRD」项必须人工裁决(补 PRD / 删页面功能 / 暂挂)
