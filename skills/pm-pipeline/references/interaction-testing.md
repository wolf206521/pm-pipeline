# 交互行为测试(interaction-testing)· 静态机检之外的行为层

> 静态机检(manifest/规则项)只能证明「结构声明完整」;按钮点了没反应、函数没定义、反馈不出现的缺陷要靠行为层测试。本文件是原型交互测试的通用做法。

## 为什么需要

真实评审中暴露的教训:批量生成/批量改写页面后,最常见的整页级缺陷是**脚本引用损坏**(数据集引用被误改、共享 js 重复/缺失)→ 页面加载即抛错 → 全部按钮 ReferenceError。静态检查完全发现不了,浏览器一点就穿帮。

## 运行器模式(test-runner)

一个临时 HTML 运行器(不进版本库),从导航清单取页面列表,逐页 iframe 加载:

1. **加载期**:捕获 window error / console error(加载即崩的页面立刻现形)
2. **点击期**:收集全部 `[data-op]` 元素逐一点击
3. **反馈断言**:点击后应出现 toast(`.toast` 可见)/ modal(`.modal-mask` 可见)/ 链接跳转(`<a href>` 天然通过)/ 状态切换;都没有 = 无反馈失败
4. **结果表**:页面 × 操作 × 通过/失败 + 详情,标题写 PASS/FAIL 供 headless 截图或 dump-dom 读取

要点:
- `<a href>` 链接点击记通过(能跳则跳,跳转即反馈)
- modal 检查后要点「取消」关掉,避免遮挡后续检查
- 权限隐藏块(perm-on hidden)里的按钮是运行器误报源:真实用户点不到,跳过或单独标注
- 运行器本身是临时工具,不入库;结果截图/清单留痕到评审记录

## 与静态机检的分工

| 层 | 工具 | 覆盖 |
|---|---|---|
| 静态 | test_prototype.py ①-⑦ | 结构/声明/规则/链接/状态覆盖 |
| 行为 | test-runner.html | 点击有反馈、无 JS 错误、函数有定义 |
| 人工 | G4 评审 | 语义正确性、视觉质量、业务合理 |

行为层失败修复后必须复跑到 0,才允许进 G4。

## 常见缺陷模式(修复优先级从高到低)

1. 数据集/共享 js 引用缺失或重复(整页瘫痪)
2. onclick 引用的函数未定义(批量生成时的半成品)
3. 操作只有 DOM 变化无 toast/modal(运行器探测不到 → 补即时反馈)
4. 重试/加载类操作反馈延迟过长(先给「正在处理」即时反馈)
